# v0.11.0

Host upgrade guide. Apply earlier upgrade guides first, then upgrade readers before
writing any v0.11 record. Complete the release prerequisites in the
[release notes](../releases/v0.11.0.md) before pinning a published artifact.

## Record formats

| Record | Candidate behavior | Host action |
| --- | --- | --- |
| Checkpoint | Feature-free writes remain version 2. Task-step, repeat-tool, routing, usage-budget and Runtime-approval features write checkpoint 3. Readers accept checkpoint 1–3 and refuse an unsupported version or unknown structural member before interpretation. | Upgrade both language readers before enabling a version-3 feature. Preserve old stored bytes and lifecycle metadata; do not relabel records. A host downgrade cannot read version 3. |
| Run event | Feature-free events remain version 1. Version 2 carries feature events such as `repeat_detected`, route decisions, task-aware lifecycle events and Runtime approval records. | Upgrade event readers before enabling the corresponding producer. Keep unknown structural members and versions as refusal conditions. |
| Policy | Policy version 2 adds routing and repeat-tool controls. Version 1 remains the published frozen graph. | Use version 2 only when configuring the new controls. The controls remain off by default; do not rewrite a stored v1 layer to imply an opt-in. |
| Run report | Report 1 remains the feature-free projection. Checkpoint-3 sources can produce the closed report-2 shape with the applicable route, repeat-tool or usage totals. | Branch on `report.version`; do not decode report 2 into a report-1 type or infer missing usage. |
| Corpus checkpoint view | The new version-1 display envelope selects frozen checkpoint 1/2 graphs or current checkpoint 3. It records original and derived byte identities separately. | Treat it as display data. A derived Plan view is never a native checkpoint, repaired revision or resume input. |
| Retained history and metadata | History entries, chunks, feedback, capture metadata, relation evidence and capture records have their own version-1 envelopes. Archive1 is the wire shape introduced in v0.11.0, with typed `(source digest, kind)` mappings and members, including `member.source`. | Use Archive1 only after verifying the release artifact. Archive1 does not promise compatibility with unpublished prototypes. Released checkpoint/event/report inventories remain unchanged. |

Historical reads and exports retain their supplied versions and metadata. A resumed
checkpoint is written in the current applicable format and digest rules; that does
not rewrite other retained records or extend retention. Read the selected record
version before interpreting its body, and never edit an old record to hide an
unsupported member or version.

The new Go `contract.DialectDraftCandidate` fields `ResearchDeclarations` and
`RetainedRead` use `Nullable[DialectDraftCandidateResearchDeclarations]` and
`Nullable[DialectDraftCandidateRetainedRead]`. Their earlier unpublished pointer
forms lost explicit JSON null. Go callers constructing these values must use
`Set: false` for absence, `Set: true, Null: true` for explicit null, or
`Set: true, Value: ...` for a value. JSON decoding sets these flags automatically.
This is a Go source API correction to new v0.11 fields; the v0.10.0 generated
contract contains neither field. Wire absence, null and non-null values remain
separate, and historical vectors are unchanged.

A durable root-author native invocation with an accepted Plan and conversational
controls (`AllowConversation` in Go, `allowConversation` in TypeScript) retains
checkpoint 3 / event 2 claim evidence before the provider call; see
[host preparation](../design/host-preparation.md) for the exact pause, release and
continuation requirements.

## Storage, history and imported archives

Hosts opting into retained history implement the `HistoryRunStore` extension of
`RunStore`: stage resource-scoped immutable objects, atomically commit run history
(and optional chat snapshot updates), then read revision-pinned heads, pages and
objects. The package does not install a persistent database or filesystem backend.
Memory stores are ephemeral conformance implementations; validate the host's
backend against the port contract. History commits do not form a transaction with
an external budget store or external side effect.

For chat snapshots, use `StoredChatScope` / `NewStoredChatScope` with the same
history-capable store and host-chosen chat identity. Restore validates the latest
snapshot and its run-to-turn binding; commit uses revision comparison. Hosts using
direct contextual sessions must explicitly acknowledge `StoredChatScope.close()` /
`Close` when ending a logical turn. This closes chat state; it does not terminalize
a run or grant execution authority.

The history APIs add explicit query and export paths: `projectHistoryRunReport`,
`writeRunFeedback`, `exportRunArchive` / `ExportRunArchive`, and
`readRunArchive` / `ReadRunArchive`. Feedback stays in retained metadata and out
of prompts; a candidate is `pending-review`, not corpus admission. Capture readers
validate recorded request/file relationships and may return replay material, but
they do not call a provider, execute tools or resume a run.

An imported archive is a detached read-only display. It provides no native object
store, RunStore, execution, tool, resume, admission or provider authority. An
optional caller digest checks the archive bytes; a self-consistent unsigned
archive does not prove original execution or provider authenticity. Keep imported
displays separate from native continuation inputs, and do not treat sanitised
views as exact source bytes.

## Adoption checklist

1. Confirm this candidate has passed the exact-source CI, full mutation, independent
   review and release gates before pinning it. Do not change the host digest based
   on this draft.
2. Upgrade TypeScript and Go readers together. Test historical records and each
   enabled version-3/version-2 path against the final released artifact.
3. Opt into one capability at a time, supplying its required durable store,
   ownership, budget, approval or upstream metadata contract. Keep each feature
   disabled where its host prerequisites are not satisfied.
4. Verify the release tarball and checksums against their attestations and pin the
   corresponding Go module version and `go.sum`. Review intervening upgrade guides
   when skipping releases.

Candidate-specific dependency, upstream-artifact and release-evidence status is in
the [candidate release notes](../releases/v0.11.0.md).
