# v0.14.0

Host upgrade guide from v0.13.2. Apply earlier upgrade guides first. This guide is written as
changes land on `main`; the release notes add their prerequisites when the release is prepared.

## An approved response on the agent wire (#309, #317)

These rows answer the "Not in this release" rows of the [v0.13.2 guide](v0.13.2.md).

| Change | Host action |
| --- | --- |
| On the durable agent wire, the request after the person's decision carries the approved call's result in the continuation's data block. Before this release, the paused invocation's recorded request was sent again, and the model was not told the result. The block's data now ends with `decidedAt`, when the decision was taken, on every engine. A takeover after the approval is answered carries the block again. (#309) | A host that reads the block's data accepts a last member `decidedAt`. Nothing else. |
| Under task steps, standalone and through the coordinator, the approved continuation goes on to the end. Before this release it sent the recorded request again and stopped `stopped`, with "no usable complete response". (#309) | Nothing. |
| After an answered approval and then a Plan pause, the Plan decision goes on, standalone and through the coordinator. Before this release it failed `HostOutcomeUnknown`, because the approval pause's invocation stayed `unknown`. (#309, #312) | Nothing for a run started on this release. A run that already failed so on v0.13.2 was not tested here; start a new run for its work. |
| A Plan decision whose continuation delegates goes on, through a takeover after the batch too. A later parent open is not given a Plan decision that the checkpoint shows taken. (#317) | Nothing for a run started on this release. |
| A recovered agent invocation whose outcome is `unknown` is sent again as recorded only where it carries the response's newest continuation: the decided approval's block, or the handoff's answer. One that does not (it ended at the approval pause, or at a handoff the response has gone on from) now gets a fresh request instead of a re-send, under task steps as well. An invocation lost after it was sent still carries the newest continuation: it is sent again as recorded, and under task steps it is refused `HostOutcomeUnknown`, as before. (#309, #317) | Nothing. Expect a fresh request, not a re-send, on that path. |
| In Go, a native Plan decision stored its checkpoint in a spelling that is not canonical text. On a store that keeps the run's history, that history reads a checkpoint only as canonical text, so any later open of such a run is refused `HistoryInputInvalid`. That was already so on v0.13.2. The writer now stores canonical text. A run whose Plan decision was stored by v0.13.2 stays refused; there is no migration. (#317) | Start a new run for the work of a run whose Plan decision was taken on v0.13.2 in Go. |

## Goal commands carry a worker's fence (#315)

A host-facing change to the goal commands and the store's goal port. Nothing changes for a host that sends every goal command through
the store itself.

| Change | Host action |
| --- | --- |
| A goal command sent through a worker's fenced view (`fencedRunStore`, `unattendedRunStore`; Go `FencedRunStore`, `UnattendedRunStore`) presents that view's fence in the store's transition, `run-goal.json`'s new `fence` member. The store decides it only while the fence is current for the command's run. A displaced worker's `create`, `pause`, `abandon` or any other command is refused `LeaseRefused` by the lease's own reason (`stale-epoch` after a takeover), and a fence of another run `resource-mismatch`, with nothing journaled, seized, sent or changed. Before this release a stale view's command was decided as the host's. | A host store kind: in `commandGoal`, check `transition.fence` against the store's own leases in the command's transaction, before the record is read for a repeat, and refuse as the lease refuses, journaling nothing; then pass `runStoreGoalConformance` (Go `CheckRunStoreGoalConformance`), whose `goal.fence.*` properties hold it. A store that ignores `fence` fails `goal.fence.stale`. A host that commands through a worker's view: expect that refusal where the worker was displaced. |
| `abandonGoal` through a worker's view takes the run's lease, so that view is stale afterwards. (#315) | Retry an abandon through the store itself, or through a view of the fence its answer holds. |
| `actor` is a label the host attests. The package and the store check nothing about who sent a command; the fence says only that the view's lease is current. (#315) | Decide who may issue a command in the host, before the call. |
| A goal refusal's record, `{version: 1, reason}`, has the shape of a lease refusal's, and a reason such as `invalid` is both. Unchanged. (#315 L-4) | Route a refusal by the error's name (`GoalRefused`, `LeaseRefused`), never by its record alone. |
| An abandon retried from a new process, after a crash between its sends and their journal, hands `cancel` the same `operation` as the attempt that crashed. The reference effect host forgets its admissions on restart and lets that cancel through again. (#315 L-2) | Make `cancel` idempotent by `operation`, or use an effect host whose admissions outlive its process: then the retry answers `already-admitted` and sends nothing again. The job's record keeps the crashed attempt's request. |
| `abandonGoal` on an achieved or abandoned objective refuses `objective-terminal` and sends nothing. Unchanged. (#315 L-6) | Stop a terminal objective's jobs, such as an achievement's waived ones, with `abandonJobs` under a command of your own. |
| A journaled `failed` delivery lets the next `create` through, although that job was never asked to stop. Unchanged. (#321's review, L-2) | Send it again with `abandonJobs` under a new command before creating the next objective. After the next objective exists, that call asks its jobs too. |
| An abandon whose deliveries can never be journaled, because `abandonJobs` always throws or the store always refuses them, holds every later `create` on the run at `abandon-unfinished`. Unchanged. (#321's review, L-1) | Start a new run for the work. |
| A required step the model marks `not-needed` ends the objective's legs (only `pending` and `in_progress` count as left), and `achieve` still requires every required step `completed`. Unchanged. (#330's review, LOW-4) | Expect such an objective to be abandoned, not achieved. |
