# v0.13.0

Host upgrade guide from v0.12.0. Apply earlier upgrade guides first. This guide is written as
changes land on `main`; the release notes add their prerequisites when the release is prepared.

## Dialect authoring: the retained-column selector is the final Spec 0.3.0 (#269)

`DIALECT_RETAINED_COLUMN_DRAFT` (TypeScript) and `DialectRetainedColumnDraft()` (Go) now select
contract `retained-column/1`, profile `base`, Spec version `0.3.0` at source commit
`27cb29bf13e4a2d58d69fe19c7ebfeb762b014fc`, with the unchanged schema digest
`sha256:0cb49f238c78391cb163a65474cc9af962df2bb1024a55c5310c2b784b2f0557` and corpus digest
`sha256:17b16ff7a9b74fe4cc81eb6f6129a6aabdd9834621d9e756aa2d4c1a3f245863`. This is the tuple
Runner v0.27.0 compiles and Runtime v0.39.0 installs. Through v0.12.0 the helpers selected the
candidate tuple `0.3.0-rc.2` at `bcac15b7537ce21879201b5e5dfe795496225121`, which those releases
refuse.

| Change | Host action |
| --- | --- |
| The helpers return the final tuple; the Runtime selector the tools send is `retained-column/1@27cb29bf13e4a2d58d69fe19c7ebfeb762b014fc`. | Pin a Runtime and Runner that install the final Spec 0.3.0 leaf (Runtime v0.39.0, Runner v0.27.0). A Runtime that installs only the RC2 leaf now refuses the selection. |
| A host that passes the RC2 tuple as `conversionContract` is refused before the Runtime with the existing "exact package-supported retained-column opt-in" refusal. | Take the tuple from the helper rather than storing a copy, and drop any stored RC2 tuple from host configuration. |
| Code that compares a selector with the RC2 tuple now sees a different selector: the version and revision differ while the digests are equal. | Compare all four members with the helper's current value; never treat equal digests as equal tuples. |
| `dialect-draft.json` admits the final tuple; checkpoints that carry the RC2 or Draft RFC0029 tuple stay inspectable and grant no new contract support. The generated Go union gains `DialectDraftConversionContractSpecOption3` (the final tuple); `Option1` (RC2) and `Option2` (Draft RFC0029) keep their meaning. | Keep stored checkpoints as they are. A Go host that switches on the union reads the final tuple from `Option3`. |

## Runtime identity and read-cache keys: no lone UTF-16 surrogates (#246)

A run whose `context.runtime` (Go `Input.Runtime`) has an `identity` or `version` holding a lone
UTF-16 surrogate is refused at its opening, before anything is sent, with failure code
`configuration` and the detail `RUNTIME_IDENTITY_REFUSED` (Go `RuntimeIdentityRefused`). In Go such a
string is one that is not valid UTF-8, the only way a Go string carries a lone surrogate. The
package never replaces it with U+FFFD. A valid surrogate pair and a literal U+FFFD are admitted and
key as written. The admitted identity is a copy: a later change to the host's object does not reach
the run.

A read whose tool name, argument values or argument member names hold a lone surrogate gets no
read-cache key and is kept in neither the chat's cache nor the run's; it is read again each time it
is asked. `readCacheKey` / `ReadCacheKeyOf` return no key for such a string.

**Go API change.** `ReadCacheKeyOf(tool string, arguments json.RawMessage, runtimeBound bool,
runtime *RuntimeIdentity)` now takes the call's raw JSON arguments instead of a `*Value`. A `*Value`
read with `ParseJSON` already holds U+FFFD for a lone surrogate escape, so `\ud800`, `\ud801` and a
literal U+FFFD would share one key; from the raw bytes the function refuses the first two and keys
the third as itself. Pass the arguments exactly as the model gave them (empty means `{}`). Arguments
that are not one JSON object, or not UTF-8, get no key. Go's detail text names both cases: "holds a
lone UTF-16 surrogate or is not valid UTF-8"; the TypeScript constant carries the same text.

| Host | Action |
| --- | --- |
| Reads the Runtime's version from an MCP answer with `JSON.parse` | Nothing changes for an ordinary version. A version with a lone surrogate is now refused instead of keyed. |
| Reads it in Go with `encoding/json` | `encoding/json` turns a lone surrogate escape into U+FFFD without saying so, and the package cannot tell that from a literal U+FFFD. Read the Runtime's answer with a reader that refuses lone surrogate escapes (as the descriptor snapshot reader does) before naming the Runtime, so both languages refuse the same answers. |
| Builds `RuntimeIdentity` from other sources | Pass valid UTF-8 / scalar text. The published Runtime stamps its version from an ASCII SemVer string, so its answers are unaffected. |

The shared cases, with the full canonical key and SHA-256 or the refusal for each, are in
`contract/vectors/chat/runtime-identity.json`.

## Read caches: only arguments their parsed form says exactly are cached (#271)

Go's read wrapper kept both read caches under what `ParseJSON` read and ran the tool with the bytes
the model wrote, so calls that read alike shared an answer: the second was served the first's without
being run. This was reachable from an ordinary model tool call. On both Go adapters, from the run's
cache and the chat's, a read of `{"id":9007199254740992}` after one of `{"id":9007199254740993}` was
served the first's answer, as were `{"q":2e400}` after `{"q":1e400}`, a repeated member name, and `1`
after `1.0`. On the native adapter, which does not check that arguments are an object, so was `[2]`
after `[1]`. With the output guard off, text that is not JSON read as `{}` and was served an ordinary
`{}`'s answer. In the chat's cache, `{"id":2,"ID":1}` was served the answer to `{"ID":1,"id":2}`,
though a Go tool decoding into a struct reads a different `id` from each.

The key formats do not change, and arguments that are still keyed keep the keys they had. This covers
the two read caches. A durable write's replay record compares the parsed form too, and is tracked
separately (#275).

**Expect a cold read cache once, after the upgrade.** A chat stored by an earlier release may hold an
answer under the key of different arguments, and a row is only a key and an entry, so it cannot be
told apart from a sound one. Chat context snapshots are therefore written at version 2, and restoring
a version 1 snapshot drops its cache rows.

| What a host sees | What to do |
| --- | --- |
| Each immutable read a stored chat had cached runs once more after the upgrade, then is cached again. It costs one tool or Runtime call per read and never a wrong answer. A version 1 snapshot's entries, ages and index are kept, so a later run can still read those results by id and they can still be evicted. | Budget for those calls where a read is metered, and do not treat them as a fault. Nothing needs migrating: the next snapshot of the chat is version 2. |
| New snapshots are version 2. The readers of v0.11.0 and v0.12.0 refuse them by their version, `UnsupportedContextSnapshotVersion`, before they read the body. | Upgrade every reader, a browser's and a server's, before it is handed a new snapshot, and do not downgrade a host while it keeps them (ADR-0024). |
| A snapshot's `version` is what says its cache rows can be trusted, and nothing else does: a row is a key and an entry, in both versions. A host that rewrites a version 1 snapshot's `version` to 2 keeps every old row, and both readers restore and serve them. No reader can detect this. | Never rewrite a stored snapshot's `version` or edit its body. Hand it to a restore as it was written, and let the next snapshot be the one that says version 2. |
| `readChatContextSnapshot` / `ReadChatContextSnapshot` read versions 1 and 2 and return a version 1 record as it was written, its cache rows included. `ChatContextSnapshot.version` is `1 \| 2` in TypeScript, and `CHAT_SNAPSHOT_VERSION` is exported. Only a restore drops the rows. | Code that reads a snapshot's `cache` directly must not serve a version 1 row. Code that compares a snapshot's bytes after a restore sees version 2 where it stored version 1. |

**Reads that are no longer cached.** These get no key from `readCacheKey` / `ReadCacheKeyOf`, are kept in neither cache, and run every time they are asked. Each costs one more call and never a wrong answer. Nothing counts or reports it, so a model that habitually writes `1.0` never has that read served. Their results are still kept in the chat's ledger.

| Language | No key, and kept in neither cache |
| --- | --- |
| Both | Arguments that are not one JSON object. Two member names at any depth that Go's `encoding/json` folds together: `ID` and `id`, and the Unicode folds it matches, such as the Kelvin sign and `k` or the long s and `s`, but not dotless i and `i`. Where the JavaScript engine's Unicode tables are newer than Go's, a pair only they know folds in TypeScript alone, so TypeScript gives it no key and Go does. A value with no JSON text of its own: out of range or non-finite, `-0`. |
| Go | A repeated member name, written alike or with an escape. A number not written exactly as `JSON.stringify` writes it: past what a float64 holds, `1.0`, `1e2`, `1E+21`, an underflow. Text that is not one JSON value, or has anything after it. |
| TypeScript | A value that is not one JSON holds: a `Date`, `undefined`, a `BigInt`. A number's spelling and a repeated name are read by `JSON.parse` before the wrapper, and the tool is run with what it read, so those key as what runs. |

**What can still share a chat key.** Whitespace, a string's escapes and the order of names that do not fold together stay out of the chat's key, as `contract/vectors/chat/cache-key.json` pins. A tool declared `contextPolicy.immutable` must answer the same for them. The run's own cache key keeps member order, so reordered arguments cost the run one more call.

**No arguments at all now run as `{}` (Go).** `WrapRead` wraps every session tool, so this holds for immutable reads, mutable reads and writes, where it used to hand the tool empty bytes. Both adapters already hand on `{}`, and with the output guard on `OutputGuard.JSON` refuses empty text first, so only a host that calls a wrapped tool directly sees the change: with the guard off, or on a draft-edit tool. Under a run store such a call used to be refused with `ContinuationNotRecoverable` and ran nothing; it now runs with `{}`, a write's as well. A host whose tool tells empty bytes from `{}` should stop relying on that.

The cases and their keys are in `contract/vectors/chat/read-arguments.json`. The published snapshot, byte for byte what the v0.12.0 tag's code writes for its reads, and what it restores as are in `contract/vectors/chat/context-snapshot-v1-cache.json`.

## Durable writes: a write is answered only from its own record (#275)

Under a run store, a non-read call was answered from any recorded row with the same fingerprint, and the fingerprint digests the request as `ParseJSON` reads it. A different write that read alike was therefore **not performed, and the caller was told it succeeded**. Run against each tag's own code, **v0.10.0, v0.11.0 and v0.12.0 all do this in Go**: a write of `{"id":9007199254740993}` followed by `{"id":9007199254740992}` runs once, as do `{"q":1.0}` and `{"q":1}`, `{"q":-0}` and `{"q":0}`, and `{"ID":1,"id":2}` and `{"id":2,"ID":1}`, which a tool decoding into a struct reads differently. v0.10.0, which has no history recorder, does the same for `{"a":{"x":1},"a":{"y":2}}` and `{"a":{"y":2}}`, and for `{"q":1e400}` and `{"q":2e400}`. v0.11.0 and v0.12.0 end the whole run on those with a storage failure (`HistoryInputInvalid`) instead, reads included, and run nothing.

The fingerprint's form does not change. Existing checkpoints read, and no record needs migrating. The decision now comes from the exact text each row records:

| A call with a recorded row's fingerprint | What it gets |
| --- | --- |
| The same bytes | Its record. It does not run. |
| Two requests the parsed form says exactly, differing in whitespace, a string's escapes or the order of names that do not fold together | Its record, as before. It does not run, so a resumed run's repeat is never performed twice. |
| Numbers whose exact values differ, such as `9007199254740993` and `9007199254740992` | A different write. It runs and gets its own row, with the same fingerprint. |
| The same values written differently: `1.0` and `1`, `-0` and `0`, a repeated name, two names `encoding/json` folds together in either order | `DurableRequestConflict`, a tool error the model reads, and the run goes on. It is neither run, which could perform a write twice, nor answered, which could report a write nothing performed. |

Any other call, read or write, whose text the record cannot hold (a repeated member name, a number out of range, a lone surrogate) gets `DurableRequestUnrecordable` before anything is claimed, and the run goes on. A row a published release recorded still answers its own bytes first.

| What a host sees | What to do |
| --- | --- |
| **Rows from a published release.** Each is judged by the `request` it recorded, so a row under the old fingerprint answers only its own write. A write a published release answered from another's record has no row of its own, so if it is asked for again it runs, for the first time, unless it can only be told apart by spelling, when it gets `DurableRequestConflict`. | Nothing to migrate. Expect the refusals below. |
| **Two rows can now share a fingerprint**, each with its own `request` and `requestDigest`. A published release reads such a book, and would answer the second from the first. | Do not downgrade a host while it keeps a run this release wrote (ADR-0024). Do not treat `fingerprint` as a row's identity; `id` is. |
| **A legitimate integer past 2^53.** In Go it runs exactly as written, and the tool receives those bytes. In TypeScript `JSON.parse` has already rounded it, so a host write under a run store holding an integer past 2^53-1 or a number read as an infinity is refused with `DurableRequestUnrecordable`, rather than performed on another id. | Where a TypeScript host tool takes such ids, declare them as strings. Which decimals `JSON.parse` rounded cannot be seen. Without a run store nothing is answered from a record and this rounding is unchanged. |
| **A spelling that repeats.** `{"amount":10.50}` runs. A later `{"amount":10.5}` in the same run scope is refused. | Handle `DurableRequestConflict` as "nothing ran": repeat the first text exactly for its result. An intentional second write needs a new run identity, as it always has. |

TypeScript's host writes never had this collision between different arguments as a tool sees them: a host tool runs the canonical JSON of what `JSON.parse` read, so `1.0` and `1` are one value and the record answers what ran. Its comparison now follows the same rule for rows another writer recorded and for a direct caller's text.

### What a host can look for in its records

The published releases record no mark on a call answered from a record. Run at v0.12.0, the second call of `{"id":9007199254740993}` and `{"id":9007199254740992}` leaves a `tool_call` event and an `operations` row and no row in `durable.dispatches`, and its tool does not run.

**Can be detected: that a call was answered from a record.** For one scope and tool, and one set of arguments as `ParseJSON` reads them, count the `tool_call` events, or the `operations` rows, against the non-read `durable.dispatches` rows. Each one over is a call answered from a record. Every release since v0.10.0 can have them, and most are legitimate: a true repeat looks the same.

**Cannot be detected from the records: whether that call was a true repeat or a different write.** The `args` of `tool_call` and of `operations` hold the parsed form, so both calls above read `{"id":9007199254740992}`. The second call's bytes were kept nowhere, and the row's `request` holds only the first's. Member order in the two case-variant calls is not kept in the events either.

**What narrows it down.** Look first at a row whose `request` differs from its own `tool_call` `args` as written, such as `9007199254740993` beside `9007199254740992`, and at any call answered from a record whose arguments hold an integer at or past 2^53, whatever its row says. After those, a tool that reads a number's spelling, or that decodes into a struct and was sent two names differing only in case. A `tool_result` identical to an earlier call's text is a sign only where the tool echoes what it was asked for.

**Only the system the tool writes to can settle it.** Check there that each write the run reports actually happened. A record that has expired, or an event page no longer retained, leaves nothing to count. A TypeScript run's `request` is already the rounded form, so a write it ran on a rounded id shows no difference at all: any integer at or past 2^53 in its `tool_call` `args` is suspect on its own.

This release does not perform a lost write again by itself. The cases and what each resumed call gets are in `contract/vectors/storage/durable-repeats.json`.
