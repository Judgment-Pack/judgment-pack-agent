# v0.13.0

Host upgrade guide from v0.12.0. Apply earlier upgrade guides first. This guide is written as
changes land on `main`; the release notes add their prerequisites when the release is prepared.

## Dialect authoring: the retained-column selector is the final Spec 0.3.0 (#269)

`DIALECT_RETAINED_COLUMN_DRAFT` (TypeScript) and `DialectRetainedColumnDraft()` (Go) now select
contract `retained-column/1`, profile `base`, Spec version `0.3.0` at source commit
`27cb29bf13e4a2d58d69fe19c7ebfeb762b014fc`, with the unchanged schema digest
`sha256:0cb49f238c78391cb163a65474cc9af962df2bb1024a55c5310c2b784b2f0557` and corpus digest
`sha256:17b16ff7a9b74fe4cc81eb6f6129a6aabdd9834621d9e756aa2d4c1a3f245863`. This is the tuple
Runner v0.27.0 compiles and Runtime v0.39.0 installs. Through v0.12.0 the helpers selected the
candidate tuple `0.3.0-rc.2` at `bcac15b7537ce21879201b5e5dfe795496225121`, which those releases
refuse.

## Runtime identity and read-cache keys: no lone UTF-16 surrogates (#246)

A run whose `context.runtime` (Go `Input.Runtime`) has an `identity` or `version` holding a lone
UTF-16 surrogate is refused at its opening, before anything is sent, with failure code
`configuration` and the detail `RUNTIME_IDENTITY_REFUSED` (Go `RuntimeIdentityRefused`). In Go such a
string is one that is not valid UTF-8, the only way a Go string carries a lone surrogate. The
package never replaces it with U+FFFD. A valid surrogate pair and a literal U+FFFD are admitted and
key as written. The admitted identity is a copy: a later change to the host's object does not reach
the run.

A read whose tool name, argument values or argument member names hold a lone surrogate gets no
read-cache key and is kept in neither the chat's cache nor the run's; it is read again each time it
is asked. `readCacheKey` / `ReadCacheKeyOf` return no key for such a string.

**Go API change.** `ReadCacheKeyOf(tool string, arguments json.RawMessage, runtimeBound bool,
runtime *RuntimeIdentity)` now takes the call's raw JSON arguments instead of a `*Value`. A `*Value`
read with `ParseJSON` already holds U+FFFD for a lone surrogate escape, so `\ud800`, `\ud801` and a
literal U+FFFD would share one key; from the raw bytes the function refuses the first two and keys
the third as itself. Pass the arguments exactly as the model gave them (empty means `{}`). Arguments
that are not one JSON object, or not UTF-8, get no key. Go's detail text names both cases: "holds a
lone UTF-16 surrogate or is not valid UTF-8"; the TypeScript constant carries the same text.

| Host | Action |
| --- | --- |
| Reads the Runtime's version from an MCP answer with `JSON.parse` | Nothing changes for an ordinary version. A version with a lone surrogate is now refused instead of keyed. |
| Reads it in Go with `encoding/json` | `encoding/json` turns a lone surrogate escape into U+FFFD without saying so, and the package cannot tell that from a literal U+FFFD. Read the Runtime's answer with a reader that refuses lone surrogate escapes (as the descriptor snapshot reader does) before naming the Runtime, so both languages refuse the same answers. |
| Builds `RuntimeIdentity` from other sources | Pass valid UTF-8 / scalar text. The published Runtime stamps its version from an ASCII SemVer string, so its answers are unaffected. |

The shared cases, with the full canonical key and SHA-256 or the refusal for each, are in
`contract/vectors/chat/runtime-identity.json`.

## Read caches: only arguments their parsed form says exactly are cached (#271)

Go's read wrapper kept both read caches under what `ParseJSON` read and ran the tool with the bytes
the model wrote, so calls that read alike shared an answer: the second was served the first's without
being run. This was reachable from an ordinary model tool call. On both Go adapters, from the run's
cache and the chat's, a read of `{"id":9007199254740992}` after one of `{"id":9007199254740993}` was
served the first's answer, as were `{"q":2e400}` after `{"q":1e400}`, a repeated member name, and `1`
after `1.0`. On the native adapter, which does not check that arguments are an object, so was `[2]`
after `[1]`. With the output guard off, text that is not JSON read as `{}` and was served an ordinary
`{}`'s answer. In the chat's cache, `{"id":2,"ID":1}` was served the answer to `{"ID":1,"id":2}`,
though a Go tool decoding into a struct reads a different `id` from each.

The key formats do not change, and arguments that are still keyed keep the keys they had. This covers
the two read caches. A durable write's replay record compares the parsed form too, and is tracked
separately (#275).

**Expect a cold read cache once, after the upgrade.** A chat stored by an earlier release may hold an
answer under the key of different arguments, and a row is only a key and an entry, so it cannot be
told apart from a sound one. Chat context snapshots are therefore written at version 2, and restoring
a version 1 snapshot drops its cache rows.

| What a host sees | What to do |
| --- | --- |
| Each immutable read a stored chat had cached runs once more after the upgrade, then is cached again. It costs one tool or Runtime call per read and never a wrong answer. A version 1 snapshot's entries, ages and index are kept, so a later run can still read those results by id and they can still be evicted. | Budget for those calls where a read is metered, and do not treat them as a fault. Nothing needs migrating: the next snapshot of the chat is version 2. |
| New snapshots are version 2. The readers of v0.11.0 and v0.12.0 refuse them by their version, `UnsupportedContextSnapshotVersion`, before they read the body. | Upgrade every reader, a browser's and a server's, before it is handed a new snapshot, and do not downgrade a host while it keeps them (ADR-0024). |
| A snapshot's `version` is what says its cache rows can be trusted, and nothing else does: a row is a key and an entry, in both versions. A host that rewrites a version 1 snapshot's `version` to 2 keeps every old row, and both readers restore and serve them. No reader can detect this. | Never rewrite a stored snapshot's `version` or edit its body. Hand it to a restore as it was written, and let the next snapshot be the one that says version 2. |
| `readChatContextSnapshot` / `ReadChatContextSnapshot` read versions 1 and 2 and return a version 1 record as it was written, its cache rows included. `ChatContextSnapshot.version` is `1 \| 2` in TypeScript, and `CHAT_SNAPSHOT_VERSION` is exported. Only a restore drops the rows. | Code that reads a snapshot's `cache` directly must not serve a version 1 row. Code that compares a snapshot's bytes after a restore sees version 2 where it stored version 1. |

**Reads that are no longer cached.** These get no key from `readCacheKey` / `ReadCacheKeyOf`, are kept in neither cache, and run every time they are asked. Each costs one more call and never a wrong answer. Nothing counts or reports it, so a model that habitually writes `1.0` never has that read served. Their results are still kept in the chat's ledger.

| Language | No key, and kept in neither cache |
| --- | --- |
| Both | Arguments that are not one JSON object. Two member names at any depth that Go's `encoding/json` folds together: `ID` and `id`, and the Unicode folds it matches, such as the Kelvin sign and `k` or the long s and `s`, but not dotless i and `i`. Where the JavaScript engine's Unicode tables are newer than Go's, a pair only they know folds in TypeScript alone, so TypeScript gives it no key and Go does. A value with no JSON text of its own: out of range or non-finite, `-0`. |
| Go | A repeated member name, written alike or with an escape. A number not written exactly as `JSON.stringify` writes it: past what a float64 holds, `1.0`, `1e2`, `1E+21`, an underflow. Text that is not one JSON value, or has anything after it. |
| TypeScript | A value that is not one JSON holds: a `Date`, `undefined`, a `BigInt`. A number's spelling and a repeated name are read by `JSON.parse` before the wrapper, and the tool is run with what it read, so those key as what runs. |

**What can still share a chat key.** Whitespace, a string's escapes and the order of names that do not fold together stay out of the chat's key, as `contract/vectors/chat/cache-key.json` pins. A tool declared `contextPolicy.immutable` must answer the same for them. The run's own cache key keeps member order, so reordered arguments cost the run one more call.

**No arguments at all now run as `{}` (Go).** `WrapRead` wraps every session tool, so this holds for immutable reads, mutable reads and writes, where it used to hand the tool empty bytes. Both adapters already hand on `{}`, and with the output guard on `OutputGuard.JSON` refuses empty text first, so only a host that calls a wrapped tool directly sees the change: with the guard off, or on a draft-edit tool. Under a run store such a call used to be refused with `ContinuationNotRecoverable` and ran nothing; it now runs with `{}`, a write's as well. A host whose tool tells empty bytes from `{}` should stop relying on that.

The cases and their keys are in `contract/vectors/chat/read-arguments.json`. The published snapshot, byte for byte what the v0.12.0 tag's code writes for its reads, and what it restores as are in `contract/vectors/chat/context-snapshot-v1-cache.json`.

## Re-authorization waits (#226)

A run can now park as `needs_reauthorization` when its effect host refuses an operation, before
admitting it, because the connection's credentials expired or were revoked. The host keeps the
credentials, their refresh and the person's action; the package receives a bounded connection
reference, the SHA-256 of the principal identity and scope labels. This builds on the durable waits
of ADR-0025 (`docs/design/storage.md`, Durable waits and Re-authorization waits). The records are
`contract/schemas/run-reauth.json` (version 1, new) and members of `run-wait.json`.

**With no credential check configured, nothing changes for a run.** `new ReferenceEffectHost(store)`
(Go `NewReferenceEffectHost(store)`), the `EffectHost` port and a certified host that never mints a
refusal behave as before: no refusal is minted, no dispatch is closed, no grant exists, a tool's error
still goes back to the model, a dispatch the run holds as unknown is still never sent again, and the
run's checkpoint and event bytes are unchanged. No checkpoint, event, lease or published report format
changes. TypeScript's `stampDeadline`, `readWaitDeadline` and `pinsFrom` gain optional parameters, and
Go's exported signatures keep their shape. Three things do apply to every host: the wait conformance kit
is stricter (below); code that switches over a wait's `reason`, its `pending` kind or an attention
event's `needs` gains the value `reauthorization` (Go `RunWaitPending.Reauthorization`); and a host or
Runtime tool that itself reports a failure of exactly `authentication`, `tool`, `not-started` now has it
recorded and reported as `authentication`, `tool`, `unknown` with no detail, because that typed failure on
a row now means one thing, a refusal the package trusted for that dispatch.

| Change | Host action |
| --- | --- |
| `new ReferenceEffectHost(store, {credentials})`; Go `NewReferenceEffectHostWith(store, ReferenceEffectHostOptions{Credentials})`. The check runs after the fence and the idempotency identity and before the admission is recorded, inside the host's serialized admission. The abort and the fence are checked again after it, so a run aborted or a lease lost during the check is not admitted. | To opt in, answer from your own credential state: `undefined` (Go `nil`) while the credentials are current, or `{cause, connection, principal, permissions, requires}`. `cause` is `expired` or `revoked`, `principal` is a SHA-256 digest that stays the same for one identity, and the labels are sorted in UTF-8 byte order without repeats. A malformed refusal, or a check that throws (Go: returns an error), admits nothing and proves nothing, and the error stays with you: the host replaces it with one fixed failure, `CredentialCheckFailed` (`unknown`, `tool`, `unknown`), so log it yourself if you need it. Keep the check bounded: other admissions wait for it. |
| A host certified with `certifyEffectHost` (Go `CertifyEffectHost`) mints the refusal itself: `reauthorizationRequired(admission, refusal)`; Go `NewReauthorizationRequired(ctx, admission, refusal)`. A refusal from a host not proven for the run's store is an ordinary failure. | At your admission boundary, before you admit: throw exactly what it returns (TypeScript, with the admission object you were handed), or return it unwrapped (Go, with the dispatch's own `ctx`). Never call `perform` for that dispatch: a `perform` after the dispatch has ended runs nothing and takes the trust back from the refusal. |

No proof means no re-authorization: reconcile the operation as any other unknown outcome. |

Refusals: `decision-required` (no action), `invalid` (another wait or connection), `identity-changed` (a `replacement`, or another principal), `stale` (before the park or after the store's time), `permission-insufficient`, and the pin revalidation's refusals. A refused resume leaves the wait holding the run. |

**Store obligations the kit checks.** A host store kind must, in the park's and the claim's own
transactions, and keep across its restarts:

- refuse a park whose disposition was minted under another fence, by owner or by epoch (`stale`), or
  whose head does not hold its operation as the never-admitted dispatch (`unbound`; `holdsNeverAdmitted` /
  `HoldsNeverAdmitted` decide it, and the kit tries a row with a result, a row still claimed, one that is
  not the last dispatch, another failure code or outcome or none, a read, another kind of row, and
  another operation, source, tool or request), changing nothing and leaving the lease held;
- when the run's approved call is unsettled, attach that approval's binding to the wait and stamp its
  expiry as the deadline's `approval` time, from the store's own record and never from the park, and keep
  that time through `limitRun`, whether the new limit is later or earlier;
- record the wait's one attention event, needing `reauthorization` and naming the connection;
- refuse a claim of a reauthorization wait with no refresh (`decision-required`), for another principal
  (`identity-changed`), with permissions that do not cover what the operation requires
  (`permission-insufficient`), or timed before the park or after the store's time (`stale`), changing
  nothing; refuse it from the approval's expiry (`deadline-passed`) and a second time
  (`already-resumed`), and bound the claim's lease by that expiry;
- record the refresh in the claim (`reauthorized`);
- end the wait at its timeout or deadline wake: refuse a late wake and a late claim, and refuse a new
  lease for the run (`closed`);
- keep the wait, the disposition, the refresh, the attached approval and those endings through a restart.

The kit does not exercise a repeat of a reauthorization park (the attached approval is not part of the
comparison) or the refusal of `reauthorized` on another wait's claim. The memory kind is the reference
for those.

**An approved act call refused for its credentials is not re-sent.** The reauthorization wait holds
that approval's binding and expiry, and the resume revalidates them, but ADR-0008's continuation
restores an approved call whose result was never written as executed with an unknown outcome, and does
not send it, whatever the refresh. The run is told the call may have run, although the effect host
refused it; the wait's disposition is the record that it was not admitted. Continue without a decision
(a decision passed for that call fails the continuation, and nothing runs). A new decision in the same
run does not send it either: with the same arguments the call is not run, its row stays unknown and the
writer answers `HostOutcomeUnknown`. A Runtime call asked with a new call id is a new operation and goes
through its own approval, with nothing carried over. Otherwise a call that is still wanted needs a new
run. From the approval's expiry the wait cannot be claimed; its `deadline` wake ends it and closes the
run.

**A re-send refused again cannot wait again.** If the effect host refuses the re-send too, the refusal is
trusted and the run stops with the proof on its view, but `parkRun` answers `unbound`: the row keeps its
place and the continuation's model or agent row follows it, so the operation is not the head's last
dispatch. Nothing ran, and that view's grant is spent. While the claim's lease is held you may open
another view of the same claim, which sends the operation once more with no new action. Otherwise treat
it as any other unknown outcome and start a new run if the call is still wanted. This is deliberate: it
fails safe, and accepting that head would widen what every park and every store accepts.

**What a host must do.**

- Refuse only when the operation cannot have been admitted: decide from your own credential state,
  before anything is sent. A provider's 401 after the call was sent is an unknown outcome, never a
  refusal.
- Keep credentials, tokens and provider errors out of `connection`, the scope labels and `actor`. The
  readers refuse extra members, an undigested principal, an unbounded connection and an unbounded actor;
  they cannot recognize a secret that fits the pattern. Pass a stable reference as `actor`, not a person's
  name or address.
- Mint a fresh wake key for each wait, as for every wait, and authenticate the person's action
  yourself. The package records `actor` and `at` as you attest them.
- Treat a replacement as a new run: it never continues the wait. Admit a new run, and end the old one
  with `limitRun` and its `deadline` wake, since a woken wait otherwise keeps holding the run.
- Keep a durable effect host's admission record across restarts, as `already-admitted` already
  requires. The reference effect host keeps its record in memory, so it does not meet this after a
  restart. What the package itself holds across one: the re-send's claim clears the typed failure before
  the dispatch, so a crash after it leaves a row no view can send, and the head's compare-and-set stops
  two views from claiming it together.

**What a host must not assume.**

- That re-authorization is retry permission. Nothing that may have been admitted is sent again by the
  package, and a wake or a refresh grants nothing.
- That the operation will be sent. The continuation does not replay it; it goes only if the run's model
  or agent asks for exactly that request again. That depends on the kind of call, not the adapter: a host
  tool's request is its arguments, so repeating them keeps its identity on every adapter, while a Runtime
  call's request carries its call id. "Exactly" means the bytes that were refused, in both languages: other
  bytes never run under the refused identity. A re-send that is not those bytes gets what any call gets from
  the row (#275): whitespace or member order answers `HostOutcomeUnknown`, another spelling of the same values
  is refused with `DurableRequestConflict`, and different numbers are another write, which runs under an
  identity of its own, so it can be performed beside the operation the grant is for. Each way the row keeps its
  typed failure and the grant stays for the refused bytes. A model that rewrites its arguments leaves the
  operation unknown.
- That the package deduplicates a new call. A Runtime call asked with a new call id is a new operation on
  any adapter, under its own identity and your approval policy; with a real model's ids that is every
  Runtime action. The grant goes unused and the refused row keeps its typed failure and unknown outcome.
- That the proof or the grant survives. The proof lives in the process that ran the dispatch and parks
  one wait; if that process ends first, or the lease is lost, the operation stays unknown. A takeover
  under a new lease gets no grant.
- That certification covers the credential check. `certifyEffectHost` does not exercise it, so nothing
  in the package verifies that a host's refusal is truthful or comes before its admission.
- That a store can tell a forged disposition. It checks the fence, the key and the head; trust in the
  mint is the package's live check, so do not expose the store's wait port to anything but the package.
- That permissions were preserved. The package compares only your labels: narrower ones that still
  cover what the operation requires continue, and the refresh records them.
- That other engines behave alike. The package's tests exercise this through the Vercel engine and Go's
  eino and agent adapters. On the Codex and Deep Agents engines only how the run ends was looked at, once
  and not by a committed test; the Vercel engine with a Runtime action is by reading.

## Durable writes: a write is answered only from its own record (#275)

Under a run store, a non-read call was answered from any recorded row with the same fingerprint, and the fingerprint digests the request as `ParseJSON` reads it. A different write that read alike was therefore **not performed, and the caller was told it succeeded**. Run against each tag's own code, **v0.10.0, v0.11.0 and v0.12.0 all do this in Go**: a write of `{"id":9007199254740993}` followed by `{"id":9007199254740992}` runs once, as do `{"q":1.0}` and `{"q":1}`, `{"q":-0}` and `{"q":0}`, and `{"ID":1,"id":2}` and `{"id":2,"ID":1}`, which a tool decoding into a struct reads differently. v0.10.0, which has no history recorder, does the same for `{"a":{"x":1},"a":{"y":2}}` and `{"a":{"y":2}}`, and for `{"q":1e400}` and `{"q":2e400}`. On a store with a history recorder, v0.11.0 and v0.12.0 end the whole run on those with a storage failure (`HistoryInputInvalid`) instead, reads included, and run nothing. On a store with only the `RunStore` methods they behave as v0.10.0 does: the first runs and the second is answered.

**On the Anthropic and Gemini wires and the text path, the published Go readers lost the text before any of this.** They rewrote a call's arguments from `float64`s, so the tool itself received `9007199254740992` for `9007199254740993`, `null` for `1e400` and `0` for `1e-400`, with or without a run store, on reads as well as writes. Every Go wire now hands the tool the model's text, byte for byte: the OpenAI-compatible stream and whole answer, Anthropic's stream and whole answer, Gemini's stream and whole answer, the text path, and the native adapter, whose host hands on what the agent wrote. A tool on those paths now receives what the model wrote, which a strict decoder may refuse where it accepted the rewritten form. What goes back to the provider on the next request is unchanged: Anthropic's and Gemini's replay still carries the parsed form of the call.

The fingerprint's form does not change. Existing checkpoints read, and no record needs migrating. The decision now comes from the exact text each row records:

| A call with a recorded row's fingerprint | What it gets |
| --- | --- |
| The same bytes | Its record. It does not run. |
| Two requests the parsed form says exactly, differing in whitespace, a string's escapes or the order of names that do not fold together | Its record, as before. It does not run, so a resumed run's repeat is never performed twice. |
| Numbers whose exact values differ, such as `9007199254740993` and `9007199254740992` | A different write. It runs and gets its own row, with the same fingerprint. |
| The same values written differently: `1.0` and `1`, `-0` and `0`, a repeated name, two names `encoding/json` folds together in either order | `DurableRequestConflict`, a tool error the model reads, and the run goes on. It is neither run, which could perform a write twice, nor answered, which could report a write nothing performed. |

Any other call, read or write, whose text the record cannot hold (a repeated member name, a number out of range, a lone surrogate, bytes that are not UTF-8) gets `DurableRequestUnrecordable` before anything is claimed, and the run goes on. A row a published release recorded still answers its own bytes first.

| What a host sees | What to do |
| --- | --- |
| **Rows from a published release.** Each is judged by the `request` it recorded, so a row under the old fingerprint answers only its own write. A write a published release answered from another's record has no row of its own, so if it is asked for again it runs, for the first time, unless it can only be told apart by spelling, when it gets `DurableRequestConflict`. | Nothing to migrate. Expect the refusals below. |
| **Two rows can now share a fingerprint**, each with its own `request` and `requestDigest`. A published release reads such a book, and would answer the second from the first. | Do not downgrade a host while it keeps a run this release wrote (ADR-0024). Do not treat `fingerprint` as a row's identity; `id` is. |
| **A legitimate integer past 2^53.** In Go it runs exactly as written, and the tool receives those bytes. In TypeScript `JSON.parse` has already rounded it, so a host write under a run store holding an integer past 2^53-1 or a number read as an infinity is refused with `DurableRequestUnrecordable`, rather than performed on another id. | Where a TypeScript host tool takes such ids, declare them as strings. Which decimals `JSON.parse` rounded cannot be seen. The AI SDK's Gemini provider writes a call's arguments out itself, so through the `vercel` engine on Gemini `1e400` already reads as `null` and runs as one. Without a run store nothing is answered from a record and this rounding is unchanged. |
| **A Go tool that reads numbers into a `float64` or a `map[string]any`.** It rounds them itself, after the harness has handed it the model's bytes. `{"id":9007199254740993}` then `{"id":9007199254740992}` are two different writes here, so both run, and that tool performs both on `9007199254740992`. A published release ran the first and answered the second. | Check every Go tool that takes large ids. Read them as strings, or decode with `json.Number` or into an `int64`. |
| **A call held for approval.** What the person is shown is what runs, byte for byte: where `approval.args` cannot say the model's text, the checkpoint keeps it in `approval.request` (version 3), and the approved call runs those bytes and is decided from the record like any other. So `{"id":9007199254740993}` runs as written, a repeat of a recorded write is answered from its record, and a second spelling of one is refused. Text the record cannot hold (a repeated name, a number out of range, a lone surrogate) is refused before anyone is asked. In TypeScript that also holds for an integer past 2^53-1, since `JSON.parse` has already rounded it. | Nothing to change. A checkpoint with `approval.request` is version 3, and a published release does not read it. |
| **A call a published release paused for approval.** Its `approval.args` is the parsed form and the model's text is gone, so the first thing checked is whether that form may have changed it: a number that is zero, not an integer or past 2^53-1, a null, a replacement character or two names that fold together. TypeScript's host writes never had this collision between different arguments as a tool sees them: a host tool runs the canonical JSON of what `JSON.parse` read, so `1.0` and `1` are one value and the record answers what ran. Its comparison now follows the same rule for rows another writer recorded and for a direct caller's text.

### What a host can look for in its records

The published releases record no mark on a call answered from a record. Run at v0.12.0, the second call of `{"id":9007199254740993}` and `{"id":9007199254740992}` leaves a `tool_call` event and an `operations` row and no row in `durable.dispatches`, and its tool does not run.

**Can be detected: that a call was answered from a record.** For one scope and tool, and one set of arguments as `ParseJSON` reads them, count the `operations` rows whose status is `complete` against the non-read `durable.dispatches` rows. Each one over is a call answered from a record. Count these rows and not the `tool_call` events, because a call the policy refused or answered `HostOutcomeUnknown` adds a `tool_call` too. A failed result answered from its record shows as `failed`, so this can undercount. Every release since v0.10.0 can have them, and most are legitimate: a true repeat looks the same.

**Cannot be detected from the records: whether that call was a true repeat or a different write.** The `args` of `tool_call` and of `operations` hold the parsed form, so both calls above read `{"id":9007199254740992}`. The second call's bytes are nowhere in the store, and the row's `request` holds only the first's. Member order in the two case-variant calls is not kept in the stored events either.

**Look first at any live stream a host kept.** The `tool_call` event a host's `Emit` received holds the model's text on the OpenAI-compatible and native paths (`9007199254740993`, then `9007199254740992`), so a host that kept those events can settle this. On the published Anthropic and Gemini wires and the text path the text was rewritten before the event and the row's `request` holds the rewritten form as well, so there is no trace.

**What narrows it down.** Look first at a row whose `request` differs from its own `tool_call` `args` as written, such as `9007199254740993` beside `9007199254740992`, and at any call answered from a record whose arguments hold an integer at or past 2^53, whatever its row says. After those, a tool that reads a number's spelling, or that decodes into a struct and was sent two names differing only in case. A `tool_result` identical to an earlier call's text is a sign only where the tool echoes what it was asked for.

**Only the system the tool writes to can settle it.** Check there that each write the run reports actually happened. A record that has expired, or an event page no longer retained, leaves nothing to count. A TypeScript run's `request` is already the rounded form, and so is a Go run's on the Anthropic and Gemini wires and the text path of a published release, so a write it ran on a rounded id shows no difference at all: any integer at or past 2^53 in its `tool_call` `args` is suspect on its own.

This release does not perform a lost write again by itself. The cases and what each resumed call gets are in `contract/vectors/storage/durable-repeats.json`.
