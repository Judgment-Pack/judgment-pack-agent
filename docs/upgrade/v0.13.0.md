# v0.13.0

Host upgrade guide from v0.12.0. Apply earlier upgrade guides first. Complete the release
prerequisites in the [release notes](../releases/v0.13.0.md) before pinning a published
artifact. A host that uses none of this release's new features writes the record versions
v0.12.0 wrote and sees its bytes, apart from the changes this guide states for every host (each section names its own), among them chat snapshot 2 with its one cold cache (#271), #328's refusal to resume a `complete` head, and, in Go, checkpoint 5 and event 3 (report 3 at its end) for a call held for approval whose arguments cannot say the model's text (#275). Every other new version below
is written only where the table's last column says.

## Record formats

Upgrade every reader of a store before any writer that can write the new versions: a reader that
predates a version refuses it before reading the body (ADR-0024), and a host must not be
downgraded while it keeps records this release wrote.

## Runtime identity and read-cache keys: no lone UTF-16 surrogates (#246)

A run whose `context.runtime` (Go `Input.Runtime`) has an `identity` or `version` holding a lone
UTF-16 surrogate is refused at its opening, before anything is sent, with failure code
`configuration` and the detail `RUNTIME_IDENTITY_REFUSED` (Go `RuntimeIdentityRefused`). In Go such a
string is one that is not valid UTF-8, the only way a Go string carries a lone surrogate. The
package never replaces it with U+FFFD. A valid surrogate pair and a literal U+FFFD are admitted and
key as written. The admitted identity is a copy: a later change to the host's object does not reach
the run.

A read whose tool name, argument values or argument member names hold a lone surrogate gets no
read-cache key and is kept in neither the chat's cache nor the run's; it is read again each time it
is asked. `readCacheKey` / `ReadCacheKeyOf` return no key for such a string.

**Go API change.** `ReadCacheKeyOf(tool string, arguments json.RawMessage, runtimeBound bool,
runtime *RuntimeIdentity)` now takes the call's raw JSON arguments instead of a `*Value`. A `*Value`
read with `ParseJSON` already holds U+FFFD for a lone surrogate escape, so `\ud800`, `\ud801` and a
literal U+FFFD would share one key; from the raw bytes the function refuses the first two and keys
the third as itself. Pass the arguments exactly as the model gave them (empty means `{}`). Arguments
that are not one JSON object, or not UTF-8, get no key. Go's detail text names both cases: "holds a
lone UTF-16 surrogate or is not valid UTF-8"; the TypeScript constant carries the same text.

| Host | Action |
| --- | --- |
| Reads the Runtime's version from an MCP answer with `JSON.parse` | Nothing changes for an ordinary version. A version with a lone surrogate is now refused instead of keyed. |
| Reads it in Go with `encoding/json` | `encoding/json` turns a lone surrogate escape into U+FFFD without saying so, and the package cannot tell that from a literal U+FFFD. Read the Runtime's answer with a reader that refuses lone surrogate escapes (as the descriptor snapshot reader does) before naming the Runtime, so both languages refuse the same answers. |
| Builds `RuntimeIdentity` from other sources | Pass valid UTF-8 / scalar text. The published Runtime stamps its version from an ASCII SemVer string, so its answers are unaffected. |

The shared cases, with the full canonical key and SHA-256 or the refusal for each, are in
`contract/vectors/chat/runtime-identity.json`.

## Agent principals: delegation is an opt-in (#260)

A host that sets nothing is unaffected: a run with no `ContextInput.principal` (Go `Input.Principal`)
writes the earlier record versions and members byte for byte. A host that sets it runs the agent under
a delegation chain from an issuing host (spec RFC 0030, a Draft; [ADR-0029](../adr/0029-agent-principals.md)).

| Change | Host action |
| --- | --- |
| A delegated run writes checkpoint 4, event 3 on its tool events and delegation refusals, and run report 3, each with `principal`. Readers from v0.10.0 onward that predate these versions refuse them by ADR-0024. | Upgrade every reader of a delegated run's records before starting one. |
| `ContextInput.principal` takes the chain's JSON text, the issuing hosts' pinned keys, the run's software, the agent-host name, an admission port and a clock. A refused chain ends the run before any request (`configuration`). | Supply them from the issuing host; the admission port answers from that host's state, afresh, within five seconds. |
| A `gateway` source needs its gateway's authority and source name on the declaration (`ToolSource.gatewayScope`, Go `ToolSource.GatewayScope`) or a delegated run refuses its calls. | Declare it for each gateway source a delegated run uses. |
| A resume under another subject, root actor or issuing host, without the run's delegation, or with one on a run that had none, is refused with failure code `stale-state`, its detail naming `principal-changed`, on a durable store as well. | Resume with the delegation the run began under, or a re-issued chain of the same three. |
| An acting Runtime call (a Runtime tool served with effect `act`) is admitted under a delegation as source `runtime`, effect `act`: refused outside the scope, past expiry and after revocation. | Issue the chain with an agent-host entry for source `runtime` naming the tool, if delegated runs use it. |
| A host tool with no source is refused past expiry and after revocation, though no scope matches it. Its read names `source: local` and never counts. | Have the port answer standing for `source: local`, and not apply scope to it. |
| A call now reads the port with counting unset at the gate and with counting set immediately before its dispatch, so a dispatched call makes at least two reads. A read answered from a cache or retained evidence makes the first only. | Nothing, if the port is idempotent for uncounted reads; count only reads with `count: true`. |
| A credential refusal under a delegation is not a delegation refusal, and counts nothing. Its re-send after a re-authorization wait (#226) is admitted again, and counted once at its dispatch; a delegation revoked or expired meanwhile refuses it by name. | Answer the port from the delegation's own state: a refreshed credential does not revive a revoked delegation. |
| A delegated run's re-authorization wait pins its principals, and the evidence of its resume must name them: other principals are `principal-changed`, before the action is read. | Add `principal` to the evidence, as for any delegated wait. |
| `gatewayScope` is refused on any source kind but `gateway`, and when its authority is not the one the source's `gatewayReceipt` pins. Go now holds its form as TypeScript does. | Declare the source as kind `gateway`, and give the mapping the pinned authority. |
| Checkpoint 3 and event 2 are read against their inventory frozen at v0.12.0, so neither can carry a principal. | Nothing: the members those versions name are unchanged. |
| Under a delegation a child starts only from a delegation that stands (a read of `source: local`, tool `delegate_tasks`) and with the narrowed link the host answers on `RunPrincipal.child` (Go `RunPrincipal.Child`); with no port, or below a link with `mayDelegate` false, its task fails `permission`, `not-started`, naming `delegation-not-permitted`. | Supply the port if delegated runs delegate: answer `{chain}` with the parent's chain text plus one link the issuing host signed, or `{refusal}`, within five seconds. |
| Once a child's link is issued, its `delegated_task` records are event 3 with the child's `principal`. The queued and running records before that, and a refused child's failed record, are event 1 with none. | Upgrade its readers with the others above, and read both forms. |
| A delegated run's lease and fence are `run-lease.json` version 2 with `principal`, and an acquisition under other principals refuses `principal-changed`. A session on a fenced store refuses a fence that does not hold its principals. | Pass the binding to `acquireLease` (`principalBinding(record)`, Go `PrincipalRecord.Binding()`) for a delegated run. |
| A store kind that hosts delegated leases keeps and returns `principal` and declares it: in TypeScript with the property `readonly leasePrincipals = true`, in Go with the method `LeasePrincipals() bool`. `fencedRunStore` refuses a delegated fence on any other, and the kit fails a TypeScript store whose member is anything but `true`. | Add the member to your lease row, declare it, and run the conformance kit's `lease.principal.*` rows, which cover the history and snapshot commits. |
| A delegated wait's pins carry `principal`, and resume evidence for it must name the same binding, or the resume refuses `evidence-missing` or `principal-changed`. | Add `principal` to the evidence you present for a delegated wait. |
| A child's read of a source has no credential check, but its `list_context`, `update_plan`, `complete_plan_step` and `request_budget_increase`, and a sourceless tool with `delegation` and a non-read effect, reach your effect host's check as `source: host`. Refused there, the whole run stops with the child's proof on its view. Nothing is dispatched or counted, and after the resume the child is not run again and its row stays `unknown` with the typed failure (`authentication`, `not-started`). The task's state depends on the engine: `interrupted` on TypeScript's `vercel` and `deepagents` with no task steps; `failed` with task steps there and in Go; on TypeScript's `codex` it stays `running` at the stop and is reported `interrupted` at the resume. | Expect a re-authorization wait that names a child's tool, and decide whether your credential check refuses `source: host`. Ask the view for the proof when the run ends, and do not wait for a particular task state. You can park on the proof when the refused row is the head's last dispatch. With children running at once and a sibling's row after it, `parkRun` refuses `unbound`: nothing more is dispatched, and the run stays stopped with its lease held until you treat the operation as any other unknown outcome. |
| A child offered part of a source under a legacy `toolListDigest` has the whole source withheld, as before: the digest is of the whole list. The guardrail lands only on the durable log in the child's scope, and nowhere with no store, and neither the parent's stream nor the host's sees it, so the child ends `complete` having read nothing, though its link request named the withheld tools. So a parent holding a legacy source with an act cannot delegate that source's read. A descriptor-snapshot source allows a subset, but only on kind `mcp` or `gateway`, with the read declared `read-external` and a receipt check. | For a source you dispatch yourself (`custom`), a snapshot is refused at start as configuration (with or without a run store, on a fresh run or at a resume: nothing is sent, and the head's bytes do not change. A stored chat's resume still moves the run's revision and the chat's context with the same bytes, and the run stays resumable), so give the reads their own source id and offer that source whole. Under a delegation, the chain has to name the new source too, or its reads are refused. For an `mcp` or `gateway` source, use a descriptor snapshot or offer the legacy source whole. |
| The wait kit holds a delegated run's principals on a re-authorization wait too, under `leasePrincipals` (Go `LeasePrincipals()`): `reauth.principal.*` and `reauth.restart.principal*`. A store that drops `pins.principal`, or writes the proof's fence back as version 1, now fails by name. | Keep both as parked, and run `runStoreWaitConformance` (Go `CheckRunStoreWaitConformance`). |

## Read caches: only arguments their parsed form says exactly are cached (#271)

Go's read wrapper kept both read caches under what `ParseJSON` read and ran the tool with the bytes
the model wrote, so calls that read alike shared an answer: the second was served the first's without
being run. This was reachable from an ordinary model tool call. On both Go adapters, from the run's
cache and the chat's, a read of `{"id":9007199254740992}` after one of `{"id":9007199254740993}` was
served the first's answer, as were `{"q":2e400}` after `{"q":1e400}`, a repeated member name, and `1`
after `1.0`. On the native adapter, which does not check that arguments are an object, so was `[2]`
after `[1]`. With the output guard off, text that is not JSON read as `{}` and was served an ordinary
`{}`'s answer. In the chat's cache, `{"id":2,"ID":1}` was served the answer to `{"ID":1,"id":2}`,
though a Go tool decoding into a struct reads a different `id` from each.

The key formats do not change, and arguments that are still keyed keep the keys they had. This covers
the two read caches. A durable write's replay record compares the parsed form too, and is tracked
separately (#275).

**Expect a cold read cache once, after the upgrade.** A chat stored by an earlier release may hold an
answer under the key of different arguments, and a row is only a key and an entry, so it cannot be
told apart from a sound one. Chat context snapshots are therefore written at version 2, and restoring
a version 1 snapshot drops its cache rows.

| What a host sees | What to do |
| --- | --- |
| Each immutable read a stored chat had cached runs once more after the upgrade, then is cached again. It costs one tool or Runtime call per read and never a wrong answer. A version 1 snapshot's entries, ages and index are kept, so a later run can still read those results by id and they can still be evicted. | Budget for those calls where a read is metered, and do not treat them as a fault. Nothing needs migrating: the next snapshot of the chat is version 2. |
| New snapshots are version 2. The readers of v0.11.0 and v0.12.0 refuse them by their version, `UnsupportedContextSnapshotVersion`, before they read the body. | Upgrade every reader, a browser's and a server's, before it is handed a new snapshot, and do not downgrade a host while it keeps them (ADR-0024). |
| A snapshot's `version` is what says its cache rows can be trusted, and nothing else does: a row is a key and an entry, in both versions. A host that rewrites a version 1 snapshot's `version` to 2 keeps every old row, and both readers restore and serve them. No reader can detect this. | Never rewrite a stored snapshot's `version` or edit its body. Hand it to a restore as it was written, and let the next snapshot be the one that says version 2. |
| `readChatContextSnapshot` / `ReadChatContextSnapshot` read versions 1 and 2 and return a version 1 record as it was written, its cache rows included. `ChatContextSnapshot.version` is `1 \| 2` in TypeScript, and `CHAT_SNAPSHOT_VERSION` is exported. Only a restore drops the rows. | Code that reads a snapshot's `cache` directly must not serve a version 1 row. Code that compares a snapshot's bytes after a restore sees version 2 where it stored version 1. |

**Reads that are no longer cached.** These get no key from `readCacheKey` / `ReadCacheKeyOf`, are kept in neither cache, and run every time they are asked. Each costs one more call and never a wrong answer. Nothing counts or reports it, so a model that habitually writes `1.0` never has that read served. Their results are still kept in the chat's ledger.

| Language | No key, and kept in neither cache |
| --- | --- |
| Both | Arguments that are not one JSON object. Two member names at any depth that Go's `encoding/json` folds together: `ID` and `id`, and the Unicode folds it matches, such as the Kelvin sign and `k` or the long s and `s`, but not dotless i and `i`. Where the JavaScript engine's Unicode tables are newer than Go's, a pair only they know folds in TypeScript alone, so TypeScript gives it no key and Go does. A value with no JSON text of its own: out of range or non-finite, `-0`. |
| Go | A repeated member name, written alike or with an escape. A number not written exactly as `JSON.stringify` writes it: past what a float64 holds, `1.0`, `1e2`, `1E+21`, an underflow. Text that is not one JSON value, or has anything after it. |
| TypeScript | A value that is not one JSON holds: a `Date`, `undefined`, a `BigInt`. A number's spelling and a repeated name are read by `JSON.parse` before the wrapper, and the tool is run with what it read, so those key as what runs. |

**What can still share a chat key.** Whitespace, a string's escapes and the order of names that do not fold together stay out of the chat's key, as `contract/vectors/chat/cache-key.json` pins. A tool declared `contextPolicy.immutable` must answer the same for them. The run's own cache key keeps member order, so reordered arguments cost the run one more call.

**No arguments at all now run as `{}` (Go).** `WrapRead` wraps every session tool, so this holds for immutable reads, mutable reads and writes, where it used to hand the tool empty bytes. Both adapters already hand on `{}`, and with the output guard on `OutputGuard.JSON` refuses empty text first, so only a host that calls a wrapped tool directly sees the change: with the guard off, or on a draft-edit tool. Under a run store such a call used to be refused with `ContinuationNotRecoverable` and ran nothing; it now runs with `{}`, a write's as well. A host whose tool tells empty bytes from `{}` should stop relying on that.

The cases and their keys are in `contract/vectors/chat/read-arguments.json`. The published snapshot, byte for byte what the v0.12.0 tag's code writes for its reads, and what it restores as are in `contract/vectors/chat/context-snapshot-v1-cache.json`.

## Durable waits, attention events and the report (#224, #228)

Nothing changes unless a host parks a run. A run that is never parked is leased as before, and a park
writes nothing into the run's checkpoint or event log, so a paused checkpoint of an earlier version
parks without being rewritten. New: the record `run-wait.json` (version 1), `storage/wait` and
`storage/waitConformance` (Go `run_wait.go`, `run_wait_conformance.go`). The design is
[Durable waits, attention and the report](../design/storage.md#durable-waits-attention-and-the-report-224-228)
and ADR-0025 decisions 2 and 6 with their amendment.

| A host that parks runs | What it must do | What happens otherwise |
| --- | --- | --- |
| Its store | Implement `WaitStore` beside its lease port, with `waitLifetime` `durable`, each transition atomic with its commits and against the run head, and keep the waits, their attention events and deliveries, each run's earliest deadline and an unsettled approval across its own restarts. Pass `runStoreWaitConformance` (Go `CheckRunStoreWaitConformance`), which is new in this release | `WaitCapabilityRefused`: `store-unsupported` (a store without the port, and the callback kind), `store-lifetime` (`MemoryRunStore`, whose waits live in its process). `admitWaits` (Go `AdmitWaits`) gives the same refusals up front. The package re-checks none of a host store's obligations: the kit certifies them |
| Parking | After a run ends paused (an asked approval, a budget pause in model requests) or after a `user_question`, call `parkRun` (Go `ParkRun`) under the fence it ran under, with a `wakeKeyDigest` of a fresh key minted for this wait alone from a cryptographic random source, and the host's evidence of each provider resource the run held (`release`) | `nothing-pending`; `not-resumable` for a pause no package input can resume (a plan decision, a provider-managed allowance), which is never parked; `wait-pending` while another wait of the run is unresumed; `checkpoint-changed`; `key-reused` for a digest another wait holds; `conflict` for another park under the same wait id. A refused park changes nothing and leaves the lease held. A committed park releases it |
| Waking | Deliver `wakeRun(store, evidence)` (Go `WakeRun`) with the wait's key and the expected event, time, timeout or deadline. An error from the store leaves the outcome unknown: read the wait to learn it | `no-wait`, `unauthenticated` (wrong key), `mismatch`, `not-due`, `stale` (another wake won), `timed-out`, `deadline-passed`. A duplicate wake returns the first disposition. A resumed wait is never woken again. A wake is never the approval or the grant |
| Resuming | `resumeParked` (Go `ResumeParked`) with the acknowledged wake, the person's decision (an approval wait) or a grant from its paused limit (a budget wait), the reconciliation of every uncertain release, and `current` evidence (the next section). Continue on the returned fence through `fencedRunStore`, with `context.approval` (Go `Input.Approval`) or the grant, as ADR-0008 continues a pause | `unacknowledged`, `already-resumed`, `decision-required`, `release-uncertain`, `invalid`, `checkpoint-changed`, and the revalidation's refusals. Nothing is leased or claimed before every check passes; the claim takes the run's next lease in the same transaction |
| A chat-bound park | TypeScript: pass the `ChatStore` to resume; it revalidates the binding before the claim, outside the store's transaction | `chat-changed`. Go has no ChatStore and refuses a chat-bound resume `chat-store-unsupported` |
| Attention | Deduplicate notifications by the attention event's `id`, the SHA-256 of `{resource, wait}`; `needs` is `approval-decision`, `budget-grant`, `question-answer`, `reauthorization` or `job-completion`. Record your delivery attempts with the store's `recordDelivery`, which keeps them apart from the event; the package and the store never send anything | A failed delivery changes no wait |
| The report | `waitReport` (Go `WaitReportOf`) reads `exportWaits`: per wait, the park, the winning wake, a deadline that ended it, a question's answer or `unanswered` end, and the resume. Pass `now` to expire content past its `retainUntil`; the store's `redactWait` removes question and answer content and keeps every identity and digest | Without `now` nothing is expired, and `exportWaits` and `readWait` return the question and answer in full until you redact them |
| Code that switches over a wait | Handle the reasons `approval`, `budget`, `question`, `reauthorization` and `job` | |

**A parked run is held.** Until its wait is resumed, the store refuses `acquireLease`, an unfenced commit
and a second park (`wait-pending`), and once a wait ended for good (a timed-out approval or budget wait,
or an expired one) all of them for good (`closed`). The resume's claim is the only way back into the run.
A question's timeout stays a resumable end.

## Deadlines, approval expiry, resume revalidation and run closure (#225, #227, #265)

Nothing changes unless a host sets a deadline or parks a run: deadlines are optional host policy and
absent by default, and an unparked run is not revalidated. New: the record `run-resume.json` (version
1), `storage/resume` (Go `run_resume.go`), and members of `run-wait.json`. Every time is the store's
clock. The design is [Deadlines, approval expiry and resume revalidation](../design/storage.md#deadlines-approval-expiry-and-resume-revalidation-225-227-265-m2)
and ADR-0025 decisions 3 and 5 with their amendments.

| Change | Host action |
| --- | --- |
| `limitRun(store, {version, resource, run})` (Go `LimitRun`) sets a run's deadline at any time. The store keeps the earliest it is given, shortens a held lease to it, grants and renews no lease past it, and stamps every unresumed wait of the run with it. A run driven through `fencedRunStore` makes no model, agent, Runtime or tool dispatch at or after it (equal time is past). An effect already admitted stays unknown until its own host reconciles it: the deadline undoes nothing and re-runs nothing. | Set it where a run must not go on past a time. A lease acquired at or after it is refused `deadline-passed`. |
| A park's `limits` (`run`, `waitMs`, `approvalTtlMs`, each 1 ms to 30 days) stamp its deadline as the earliest of the run's deadline, the park time plus `waitMs` and, for an approval wait, the park time plus `approvalTtlMs`. From the deadline no wake, answer or claim of the wait is accepted. | Deliver a `deadline` wake at the deadline: it records `expired` and ends the wait, and its run, for good (`closed`). A question its deadline ends before an answer is `unanswered`. |
| An approval wait is unattended approval: `parkRun` refuses one without `limits.approvalTtlMs` (`approval-ttl-required`) and records the call's binding (its call id, the digest of `{name, tool, args, runtime?}` and its source). A decision or a claim at or after the expiry is refused. From the claim until the approved call settles, the expiry bounds every lease of the run, and every checkpoint committed meanwhile must carry exactly the reviewed call (`approval-changed`). | Give every approval wait a TTL. If the call has not settled by the expiry, deliver the `deadline` wake on the resumed wait, due at the approval's expiry: it records the call's outcome unknown and closes the run. Reconcile the effect through your effect host's admission record. Re-asking needs a new request and a new decision. |

## Re-authorization waits (#226)

A run can now park as `needs_reauthorization` when its effect host refuses an operation, before
admitting it, because the connection's credentials expired or were revoked. The host keeps the
credentials, their refresh and the person's action; the package receives a bounded connection
reference, the SHA-256 of the principal identity and scope labels. This builds on the durable waits
above (`docs/design/storage.md`, Durable waits and Re-authorization waits). The records are
`contract/schemas/run-reauth.json` (version 1, new) and members of `run-wait.json`.

**With no credential check configured, no refusal is minted, and a run changes only in the two cases named
below.** `new ReferenceEffectHost(store)` (Go `NewReferenceEffectHost(store)`), the `EffectHost` port and a
certified host that never mints a refusal behave as before: no dispatch is closed, no grant exists, a tool's
error still goes back to the model, a dispatch the run holds as unknown is still never sent again, and apart
from those two cases the run's checkpoint and event bytes are unchanged. Re-authorization itself changes no
checkpoint, event, lease or published report format. TypeScript's `stampDeadline`, `readWaitDeadline` and `pinsFrom` gain optional
parameters, and Go's exported signatures keep their shape. Four things do apply to every host:

- the wait conformance kit, new in this release, includes the `reauth.*` properties (below);
- code that switches over a wait's `reason`, its `pending` kind or an attention event's `needs` gains the
  value `reauthorization` (Go `RunWaitPending.Reauthorization`);
- **under a run store**, a host or Runtime tool that itself reports a failure of exactly `authentication`,
  `tool`, `not-started` now has it recorded and reported as `authentication`, `tool`, `unknown` with no
  detail, because that typed failure on a row now means one thing, a refusal the package trusted for that
  dispatch. With no run store it still reaches the model as written;
- **under a fenced view**, a `perform` your effect host calls after its dispatch has ended runs nothing and
  is refused (`LeaseRefused` `invalid`).

**Store obligations the kit checks.** A host store kind must, in the park's and the claim's own
transactions, and keep across its restarts:

- refuse a park whose disposition was minted under another fence, by owner or by epoch (`stale`), or
  whose head does not hold its operation as the never-admitted dispatch (`unbound`; `holdsNeverAdmitted` /
  `HoldsNeverAdmitted` decide it, and the kit tries a row with a result, a row still claimed, one that is
  not the last dispatch, another failure code or outcome or none, a read, another kind of row, and
  another operation, source, tool or request), changing nothing and leaving the lease held;
- when the run's approved call is unsettled, attach that approval's binding to the wait and stamp its
  expiry as the deadline's `approval` time, from the store's own record and never from the park, and keep
  that time through `limitRun`, whether the new limit is later or earlier;
- record the wait's one attention event, needing `reauthorization` and naming the connection;
- refuse a claim of a reauthorization wait with no refresh (`decision-required`), for another principal
  (`identity-changed`), with permissions that do not cover what the operation requires
  (`permission-insufficient`), or timed before the park or after the store's time (`stale`), changing
  nothing; refuse it from the approval's expiry (`deadline-passed`) and a second time
  (`already-resumed`), and bound the claim's lease by that expiry;
- record the refresh in the claim (`reauthorized`);
- end the wait at its timeout or deadline wake: refuse a late wake and a late claim, and refuse a new
  lease for the run (`closed`);
- keep the wait, the disposition, the refresh, the attached approval and those endings through a restart.

The kit does not exercise a repeat of a reauthorization park (the attached approval is not part of the
comparison) or the refusal of `reauthorized` on another wait's claim. The memory kind is the reference
for those.

**An approved act call refused for its credentials is not re-sent.** The reauthorization wait holds
that approval's binding and expiry, and the resume revalidates them, but ADR-0008's continuation
restores an approved call whose result was never written as executed with an unknown outcome, and does
not send it, whatever the refresh. The run is told the call may have run, although the effect host
refused it; the wait's disposition is the record that it was not admitted. Continue without a decision
(a decision passed for that call fails the continuation, and nothing runs). A new decision in the same
run does not send it either: with the same arguments the call is not run, its row stays unknown and the
writer answers `HostOutcomeUnknown`. A Runtime call asked with a new call id is a new operation and goes
through its own approval, with nothing carried over. Otherwise a call that is still wanted needs a new
run. From the approval's expiry the wait cannot be claimed; its `deadline` wake ends it and closes the
run.

**A re-send refused again cannot wait again.** If the effect host refuses the re-send too, the refusal is
trusted and the run stops with the proof on its view, but `parkRun` answers `unbound`: the row keeps its
place and the continuation's model or agent row follows it, so the operation is not the head's last
dispatch. Nothing ran, and that view's grant is spent. While the claim's lease is held you may open
another view of the same claim, which sends the operation once more with no new action. Otherwise treat
it as any other unknown outcome and start a new run if the call is still wanted. This is deliberate: it
fails safe, and accepting that head would widen what every park and every store accepts.

**What a host must do.**

- Refuse only when the operation cannot have been admitted: decide from your own credential state,
  before anything is sent. A provider's 401 after the call was sent is an unknown outcome, never a
  refusal.
- Keep credentials, tokens and provider errors out of `connection`, the scope labels and `actor`. The
  readers refuse extra members, an undigested principal, an unbounded connection and an unbounded actor;
  they cannot recognize a secret that fits the pattern. Pass a stable reference as `actor`, not a person's
  name or address.
- Mint a fresh wake key for each wait, as for every wait, and authenticate the person's action
  yourself. The package records `actor` and `at` as you attest them.
- Treat a replacement as a new run: it never continues the wait. Admit a new run, and end the old one
  with `limitRun` and its `deadline` wake, since a woken wait otherwise keeps holding the run.
- Keep a durable effect host's admission record across restarts, as `already-admitted` already
  requires. The reference effect host keeps its record in memory, so it does not meet this after a
  restart. What the package itself holds across one: the re-send's claim clears the typed failure before
  the dispatch, so a crash after it leaves a row no view can send, and the head's compare-and-set stops
  two views from claiming it together.

**What a host must not assume.**

- That re-authorization is retry permission. Nothing that may have been admitted is sent again by the
  package, and a wake or a refresh grants nothing.
- That the operation will be sent. The continuation does not replay it; it goes only if the run's model
  or agent asks for exactly that request again. That depends on the kind of call, not the adapter: a host
  tool's request is its arguments, so repeating them keeps its identity on every adapter, while a Runtime
  call's request carries its call id. "Exactly" means the bytes that were refused, in both languages: other
  bytes never run under the refused identity. A re-send that is not those bytes gets what any call gets from
  the row (#275): whitespace or member order answers `HostOutcomeUnknown`, another spelling of the same values
  is refused with `DurableRequestConflict`, and different numbers are another write, which runs under an
  identity of its own, so it can be performed beside the operation the grant is for. Each way the row keeps its
  typed failure and the grant stays for the refused bytes. A model that rewrites its arguments leaves the
  operation unknown.
- That the package deduplicates a new call. A Runtime call asked with a new call id is a new operation on
  any adapter, under its own identity and your approval policy; with a real model's ids that is every
  Runtime action. The grant goes unused and the refused row keeps its typed failure and unknown outcome.
- That the proof or the grant survives. The proof lives in the process that ran the dispatch and parks
  one wait; if that process ends first, or the lease is lost, the operation stays unknown. A takeover
  under a new lease gets no grant.
- That certification covers the credential check. `certifyEffectHost` does not exercise it, so nothing
  in the package verifies that a host's refusal is truthful or comes before its admission.
- That a store can tell a forged disposition. It checks the fence, the key and the head; trust in the
  mint is the package's live check, so do not expose the store's wait port to anything but the package.
- That permissions were preserved. The package compares only your labels: narrower ones that still
  cover what the operation requires continue, and the refresh records them.
- That other engines behave alike. The package's tests exercise this through the Vercel engine and Go's
  eino and agent adapters. On the Codex and Deep Agents engines only how the run ends was looked at, once
  and not by a committed test; the Vercel engine with a Runtime action is by reading.

## Durable writes: a write is answered only from its own record (#275)

Under a run store, a non-read call was answered from any recorded row with the same fingerprint, and the fingerprint digests the request as `ParseJSON` reads it. A different write that read alike was therefore **not performed, and the caller was told it succeeded**. Run against each tag's own code, **v0.10.0, v0.11.0 and v0.12.0 all do this in Go**: a write of `{"id":9007199254740993}` followed by `{"id":9007199254740992}` runs once, as do `{"q":1.0}` and `{"q":1}`, `{"q":-0}` and `{"q":0}`, and `{"ID":1,"id":2}` and `{"id":2,"ID":1}`, which a tool decoding into a struct reads differently. v0.10.0, which has no history recorder, does the same for `{"a":{"x":1},"a":{"y":2}}` and `{"a":{"y":2}}`, and for `{"q":1e400}` and `{"q":2e400}`. On a store with a history recorder, v0.11.0 and v0.12.0 end the whole run on those with a storage failure (`HistoryInputInvalid`) instead, reads included, and run nothing. On a store with only the `RunStore` methods they behave as v0.10.0 does: the first runs and the second is answered.

**On the Anthropic and Gemini wires and the text path, the published Go readers lost the text before any of this.** They rewrote a call's arguments from `float64`s, so the tool itself received `9007199254740992` for `9007199254740993`, `null` for `1e400` and `0` for `1e-400`, with or without a run store, on reads as well as writes. Every Go wire now hands the tool the model's text, byte for byte: the OpenAI-compatible stream and whole answer, Anthropic's stream and whole answer, Gemini's stream and whole answer, the text path, and the native adapter, whose host hands on what the agent wrote. A tool on those paths now receives what the model wrote, which a strict decoder may refuse where it accepted the rewritten form. The readers have rewritten these since v0.3.0, so a host checking older records should look that far back. What goes back to the provider now says the same: where the parsed form cannot say a call and the record could hold it, the next request holds the model's text.

The fingerprint's form does not change. Existing checkpoints read, and no record needs migrating. The decision now comes from the exact text each row records:

| A call with a recorded row's fingerprint | What it gets |
| --- | --- |
| The same bytes | Its record. It does not run. |
| Two requests the parsed form says exactly, differing in whitespace, a string's escapes or the order of names that do not fold together | Its record, as before. It does not run, so a resumed run's repeat is never performed twice. |
| A request the parsed form says exactly, beside a recorded text it does not say: `9007199254740992` after `9007199254740993`, `10.5` after `10.50`, `0` after `1e-400`, `7` after `7.0000000000000000001` | `DurableRequestConflict`. It is what the recorded text reads as, so it may be a copy from the model's own history, and running it would be a second write on another id. |
| Other numbers whose exact values differ, such as `9007199254740993` after `9007199254740992` | A different write. It runs and gets its own row, with the same fingerprint. |
| The same values written differently: `1.0` and `1`, `-0` and `0`, a repeated name, two names `encoding/json` folds together in either order | `DurableRequestConflict`, a tool error the model reads, and the run goes on. It is neither run, which could perform a write twice, nor answered, which could report a write nothing performed. |

**What the first conflict row costs.** A legitimate neighbour written after a text the parsed form cannot say, such as a real `9007199254740992` after `9007199254740993`, gets a named refusal in that run and is not performed. The other order runs both. It is the price of never running a second write for a model that copied its own history. The refusal tells the model to repeat the earlier text for its result, and to tell the person if this is a different write, which needs a new run identity. **The model can follow that in a run this release started:** every API family now writes a call back as the model wrote it where the parsed form cannot say it and the record could hold it, on the next request and on a resumed run's first request, so a copy is the same bytes and is answered from the record. Every other call's body is unchanged. In a run a published release started, a resumed first request still holds the parsed form, because that is all the record has. A copy of it gets the refusal, and the advice cannot be followed there; it fails closed and the run goes on. What the record cannot hold (a number out of range, a repeated name, a lone surrogate) goes back in its parsed form, as published, since a call holding it is refused and no copy can reach a row. **Not established:** how a real provider treats a number's own text written back in its history, such as `9007199254740993` or `10.50` in Anthropic's `input`. All of this was driven with scripted responses.

Any other call, read or write, whose text the record cannot hold (a repeated member name, a number out of range, a lone surrogate, bytes that are not UTF-8) gets `DurableRequestUnrecordable` before anything is claimed, and the run goes on. A row a published release recorded still answers its own bytes first.

### If you show or bind an approval from a stored record

`approval.args`, and the `args` of a stored `approval_requested` event, are the parsed form, so they can hold another number than the one that runs: `9007199254740992` where `9007199254740993` runs, `10.5` where `10.50` runs. If your host builds an approval card or an approval reference from a checkpoint or a stored event, it has to change, and **a host that has not changed fails closed**: approving a call whose record keeps its text, such as `10.50` or `9007199254740993`, is refused with the named failure `ApprovalNotShown`, stale-state, and nothing runs. The pause stands, so the same call can be approved once the host has moved. That is the cost: until your host moves, these approvals refuse, including ordinary amounts like `10.50`. A call with no text kept, such as `{"id":7}`, goes on as it was, with the same bytes and the same version.

1. **Show the text the package gives you, as a string.** Call `approvalShownArguments(approval)` in TypeScript (`@judgment-pack/harness/contract`) or `runcontext.ApprovalShownArguments(approval)` in Go, with the checkpoint's `approval` or an `approval_requested` event (`ApprovalEventArguments` in Go). It returns exactly the text the approved call runs. Do not parse it to display it: parsing `9007199254740993` and writing it again in JavaScript shows `9007199254740992`, whatever the record holds.
2. **Bind your approval reference to the digest of that text.** Call `approvalShownDigest(approval)` or `runcontext.ApprovalShownDigest(approval)`. It is the SHA-256 of the text's UTF-8 bytes and is the same in both languages. A digest over `args` cannot tell `9007199254740992` from `9007199254740993`, and neither can a digest over text your host wrote from parsed arguments. A reference your host stored before moving will stop matching, so derive it again from the record, and tell people a paused approval may need showing again.
3. **Send that digest with the decision,** as `shownDigest` beside `callId` and `approved`. It is required to approve a call whose record keeps its text, and a digest you send with an approval must match, on any call. A person's refusal needs none, and a well-formed digest on a refusal is taken and ignored, since a refusal runs nothing. The package does not store it, and no record format changes for it. A run parked for the decision takes it the same way: `resumeParked` (Go `ResumeParked`) refuses a malformed digest (`decision-required`, approved or refused, with nothing claimed) and returns the decision with the digest for the continuation to check. It checks only the form. A digest that is well formed but wrong, or none where one is required, is refused by the continuation after `resumeParked` has claimed the wait: nothing ran, the head and the approval are unchanged, and `resumeParked` answers `already-resumed` from then on, which does not mean someone else took it. Continue with the right digest on the claim's fence, or on a new lease once that one has ended, before the approval expires; from the expiry the deadline wake ends the wait and closes the run. The digest proves your host read the text, not that the person saw it. A host that sends the digest but still builds its card from `args` defeats the check, so move the card and the digest in the same change, and have the digest come back from where the card is rendered.
4. **Read checkpoints 5 and 6 and event 3.** A held call whose `args` cannot say its text moves its checkpoint to version 5, or 6 for a delegated run, and its `approval_requested` to event 3 with the text in `request`. A published release refuses these (ADR-0024), so upgrade readers before writers.

The live `approval_requested` event's `args` already hold the text, as JSON numbers: a client that parses them has the same problem, so step 1 applies there too.

TypeScript's host writes never had this collision between different arguments as a tool sees them: a host tool runs the canonical JSON of what `JSON.parse` read, so `1.0` and `1` are one value and the record answers what ran. Its comparison now follows the same rule for rows another writer recorded and for a direct caller's text.

### What a host can look for in its records

The published releases record no mark on a call answered from a record. Run at v0.12.0, the second call of `{"id":9007199254740993}` and `{"id":9007199254740992}` leaves a `tool_call` event and an `operations` row and no row in `durable.dispatches`, and its tool does not run.

**Can be detected: that a call was answered from a record.** For one scope and tool, and one set of arguments as `ParseJSON` reads them, count the `operations` rows whose status is `complete` against the non-read `durable.dispatches` rows. Each one over is a call answered from a record. Count these rows and not the `tool_call` events, because a call the policy refused or answered `HostOutcomeUnknown` adds a `tool_call` too. A failed result answered from its record shows as `failed`, so this can undercount. Every release since v0.10.0 can have them, and most are legitimate: a true repeat looks the same.

**Cannot be detected from the records: whether that call was a true repeat or a different write.** The `args` of `tool_call` and of `operations` hold the parsed form, so both calls above read `{"id":9007199254740992}`. The second call's bytes are nowhere in the store, and the row's `request` holds only the first's. Member order in the two case-variant calls is not kept in the stored events either.

**Look first at any live stream a host kept.** The `tool_call` event a host's `Emit` received holds the model's text on the OpenAI-compatible and native paths (`9007199254740993`, then `9007199254740992`), so a host that kept those events can settle this. On the published Anthropic and Gemini wires and the text path the text was rewritten before the event and the row's `request` holds the rewritten form as well, so neither shows it. On the text path, a kept copy of the model's own reply may still hold what it wrote.

**What narrows it down.** Look first at a row whose `request` differs from its own `tool_call` `args` as written, such as `9007199254740993` beside `9007199254740992`, and at any call answered from a record whose arguments hold an integer at or past 2^53, whatever its row says. After those, a tool that reads a number's spelling, or that decodes into a struct and was sent two names differing only in case. A `tool_result` identical to an earlier call's text is a sign only where the tool echoes what it was asked for.

**Only the system the tool writes to can settle it.** Check there that each write the run reports actually happened. A record that has expired, or an event page no longer retained, leaves nothing to count. A TypeScript run's `request` is already the rounded form, and so is a Go run's on the Anthropic and Gemini wires and the text path of a published release, so a write it ran on a rounded id shows no difference at all: any integer at or past 2^53 in its `tool_call` `args` is suspect on its own.

This release does not perform a lost write again by itself. The cases and what each resumed call gets are in `contract/vectors/storage/durable-repeats.json`.

## Hosts that enroll their offers, in Go (#289)

This section matters only to a Go host that sets `adapter.Run.EnrollContext`; a run with none keeps a marker per open and its events, on failure paths too. A search of the organization's code found no enrolling host, which is weak evidence.

Before this release, a run with a source tool under such a host was refused with `ContextEnrollmentRefused` once it opened its context a second time on one gate. Each open framed the tool's description with a new marker, and the gate compares bytes. That hit a first run after its first batch on the agent path, after a child's read had already been dispatched and counted. It hit a resumed handoff too. A new gate per attempt completed on the next resume, and one kept gate was refused every time.
