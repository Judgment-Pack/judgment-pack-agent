# v0.9.1 Undici assessment

[Issue #185](https://github.com/Judgment-Pack/judgment-pack-agent/issues/185) addresses
[GHSA-4qv8-2p9j-2685](https://github.com/advisories/GHSA-4qv8-2p9j-2685) (retained EventSource state)
and [GHSA-f72v-6w45-q472](https://github.com/advisories/GHSA-f72v-6w45-q472) (non-lowercase SRI
algorithm tokens). The advisories identify 7.30.1 and 8.12.2 as patched for both behaviors.
[PR #184](https://github.com/Judgment-Pack/judgment-pack-agent/pull/184) records current audit,
checklist, CI and review evidence. Earlier clean audits are observations at their query time;
the subsequent RequestSession checklist and PR audit both reported these two identifiers.

## Compatible installed paths

The baseline lock and actual installation had one Undici 8.11.2 copy. jsdom required `^8.10.2`,
but `@ai-sdk/provider-utils` required `^7.29.0` and received the same incompatible 8.x copy;
`npm ls undici --all` reported that mismatch. Updating only the root would leave this contract
incorrect. The compatible correction changes the root to 8.12.2 and adds a nested 7.30.1 copy:

| Installed owner | Declared range | Corrected actual resolution |
| --- | --- | --- |
| `@ai-sdk/provider-utils@5.0.55` | `^7.29.0` | `@ai-sdk/provider-utils/node_modules/undici@7.30.1` |
| `jsdom@30.1.1` (development) | `^8.10.2` | root `undici@8.12.2` |

Normal npm 10.9.8 resolution/install passed and `npm ls` then exited successfully. The root
8.x record is now correctly development-only. These are the only changed/added lock records;
no manifest, direct dependency, override, unrelated version or runtime boundary changes.
The inventory walks actual installed package metadata and nested node_modules, including dev
and extraneous copies, and checks each declared owner range against its actual resolution.

## Bounded regression evidence

Handwritten controls use tiny finite fixtures on each actual installed major line. EventSource
cases bound retained data-field count, buffered chunk count, unfinished-line length, individual
metadata bytes and combined metadata bytes, with legitimate completed events as a positive control.
Item-count cases reduce the real parser instance's internal count limits to two as an isolated
test seam, then supply three fields/chunks; the byte-bound cases use four-byte limits. These are
not new public parser settings, installed source patches or memory/stress tests.

Public Undici fetch calls use tiny data URLs. Matching and mismatching SHA-256/384/512 metadata
with uppercase and mixed-case tokens must respectively succeed and refuse; a mixed-case stronger
hash must still win over a matching weaker hash. Lowercase verification is a positive/refusal
control. No external service receives these requests.

Each isolated prior version (8.11.2 and 7.29.0) fails 14 intended assertions and passes two
legitimate controls. No import error, timeout or stress outcome counts as a regression. Both
fixed major lines plus the inventory guards pass 35 focused checks. The guards also detect an
affected nested copy hidden by a fixed root and a fixed but incompatible owner major. The existing
packed-test step runs these controls in CI.

## Affected consumers and limits

The development consumer imports jsdom and constructs/closes a tiny document successfully. A fresh
installed harness consumer resolves runtime Undici 7.30.1, imports actual provider-utils, verifies
SRI through that owner's Undici, and parses a legitimate completed SSE event. The affected Vercel
entrypoint passes native import, browser bundle and generated-declaration resolution checks.
Existing 76-entrypoint, Zod and body-parser coverage remains in the default packed check; focused
work reused that evidence and the unchanged build rather than repeating those matrices.

An existing-lock runtime fixture removes its temporary old-Undici seeding pin before installing
the harness candidate. Its compatible provider-utils path still resolves affected 7.29.0 after
the candidate install. This explicit transitive refresh selects 7.30.1, leaves the consumer
manifest unchanged, and passes the affected SDK/SRI/SSE checks:

```sh
npm update undici --ignore-scripts --no-audit --no-fund
```

This establishes the refresh only for that tested graph. A repository lock does not impose its
transitive selection on hosts; inspect each actual runtime and development path, review/commit
the consumer lock and audit that application separately. Hosts with jsdom must also inspect its
separate development resolution. Consumer guards approve the selected verified versions; a
changed selection requires fresh assessment rather than an assumed passing result.

The checks cover these corrected behaviors with finite limits, not general server resource safety,
all Undici options or every upstream security fix in the releases. Deliberately disabled parser
limits are outside this evidence. This npm dependency correction does not update Node's bundled
Undici or browser-native fetch/EventSource implementations. No suppression, reachability exception
or application workaround is used. [#161](https://github.com/Judgment-Pack/judgment-pack-agent/issues/161)
remains separate undated upstream follow-up outside v0.9.1.
