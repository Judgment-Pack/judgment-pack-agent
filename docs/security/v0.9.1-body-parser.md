# v0.9.1 body-parser assessment

[Issue #178](https://github.com/Judgment-Pack/judgment-pack-agent/issues/178) addresses
[GHSA-27r3-jxmh-p828](https://github.com/advisories/GHSA-27r3-jxmh-p828), which lists body-parser
2.x below 2.4.0 as affected. This is separate from the Zod correction in
[#176](https://github.com/Judgment-Pack/judgment-pack-agent/issues/176) and its
[artifact/consumer evidence](v0.9.1-zod.md). The implementing pull request records current
dependency-audit, complete-checklist, exact-head CI and review results.

## Compatible upstream selection and artifact

The repository lock changes body-parser 2.3.0 to the published 2.4.0 release. The harness's
manifest is unchanged: no direct body-parser dependency, override or vendor patch is added.
2.4.0 tightens its content-type, iconv-lite and qs ranges; the existing lock nodes already satisfy
them, so no other package node or version changes. The installed repository path is:

```text
@judgment-pack/harness
  @modelcontextprotocol/sdk 1.32.1 (express ^5.2.1)
    express 5.2.1 (body-parser ^2.2.1)
      body-parser 2.4.0
```

The SDK's supported Express server helper installs Express's JSON parser. This identifies an
installed SDK dependency path; it does not assert that every harness host creates that server.

The [2.4.0 release](https://github.com/expressjs/body-parser/releases/tag/v2.4.0) includes
[the decoder lifecycle correction](https://github.com/expressjs/body-parser/commit/f7075eae3a84c3473ab4bf0a777da28db208e916).
It detaches and destroys a completed decompressor while retaining an error listener, drains the
remaining request, and refuses an unsupported verified charset before creating the decoder.
The release commit is `b4744d739e1e2e5257f2ddac31eed191aa5152a4`, one commit after that fix;
[the intervening diff](https://github.com/expressjs/body-parser/compare/f7075eae3a84c3473ab4bf0a777da28db208e916...b4744d739e1e2e5257f2ddac31eed191aa5152a4)
changes release metadata/history only.

On 2026-10-23 the downloaded 2.4.0 tarball's actual SHA-512 matched both published registry
metadata and the installed lock:

```text
sha512-Ifk1KcLrxaGt1occQagQNFNNOqRt1LFuehEnHHzB8Z6cRgIxRU1TBaiIsUiCdA+gy5PL7Y1IX31DNKkRmxtXjQ==
```

Its `lib/read.js` and the installed file match the official v2.4.0 source byte for byte
(Git blob `ab48aba62913b346cb4e81db9750355bd328404b`). This is artifact-integrity and source-file
comparison evidence; the separate Zod provenance verification is not attributed to body-parser.

## Bounded regression and consumer evidence

Three handwritten controls use tiny JSON and compressed frames with three trailing bytes. Deflate
and gzip decoding must complete while the request is still open, detach only their decoder,
destroy it with a retained late-error listener, and allow request completion. A separate raw-body
consumer must still receive every byte. An unsupported charset with verification must be refused
before any decoder is piped. These assertions pass on 2.4.0 and all three fail at the intended
cleanup/early-rejection assertion on an isolated 2.3.0 installation; no missing import, timeout or
uncaught process exception counts as a caught regression.

A fourth fixture refuses an affected SDK-owned Express/parser copy even when an unrelated root
copy is fixed. The existing packed-test entry runs these controls in CI. A focused packed probe
also imports the supported SDK ESM client and Express server helper and completes a tiny delayed
compressed HTTP request through that helper on loopback. The unchanged harness build and earlier
Zod regression/artifact evidence were reused.

Fresh installation selected MCP SDK 1.32.1, compatible Express 5.3.0 and body-parser 2.4.0. This
does not update Express in the repository lock, which remains 5.2.1. An existing-lock fixture
removed its temporary old-parser seeding pin before installing the harness candidate; its MCP
1.32.1 / Express 5.2.1 path still resolved affected body-parser 2.3.0 afterward. The same fixture
resolved 2.4.0 and passed the supported SDK/HTTP completion checks after:

```sh
npm update body-parser --ignore-scripts --no-audit --no-fund
```

The consumer manifest remained unchanged, with no direct body-parser dependency. This verifies
a compatible transitive refresh for that exact graph, not arbitrary consuming applications.
Review and commit the consumer lock changes, inspect the actual SDK/Express path, and audit its
graph separately. A repository lock is not a published constraint on the consumer's transitive
dependency selection; the candidate install alone did not remediate the demonstrated old lock.

No advisory suppression, reachability exception, parser configuration workaround or admission
boundary change is used. The fixtures address this corrected lifecycle, not all compressed-body
or server resource behavior. [#161](https://github.com/Judgment-Pack/judgment-pack-agent/issues/161)
remains separate undated upstream follow-up outside v0.9.1.
